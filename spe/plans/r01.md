# Google Photos MCP (local stdio, Picker API) with SPE round 1

## Context

You want Claude to get photos you just took on your Android phone straight from Google Photos. Today you open Google Photos in a browser, download the files, and point Claude at the paths.

Research changed the approach.
- Google removed full-library read access on 2025-03-31 "to improve user privacy" (Google developer blog, 2024-09-18). An app can no longer search your library by itself.
- The only approved replacement is the Picker API. You select the photos in a Google page, and the app downloads exactly those.
- The Picker strips GPS from every file and gives no location field. Time taken, camera, lens, and exposure data remain. You can still filter by place, because the picker's own search box takes place names.
- You chose these options. The Picker opens on the laptop, so you use one device. The server runs as a local stdio server, and Cloudflare comes later. Evals run against your real Google Photos. Each round has a $50 spend cap.
- Dropped options: private or reverse-engineered APIs (against Google's terms), browser automation (too brittle), Syncthing, Immich, and Drive sync (extra apps), and adb (needs the same Wi-Fi).

**Your new flow.** You ask Claude for photos. A Google Photos picker tab opens in your laptop browser, already signed in. You search or scroll, select the photos, and click Done. The tab closes. Claude gets the original files in a temp folder, plus their metadata, and does the task. No downloads, no paths, no cleanup.

## Architecture

- **Stack.** TypeScript stdio server using `@modelcontextprotocol/sdk`, `zod`, `vitest`, and `biome`, matching `~/Desktop/googlehealth`. All logs go to stderr.
- **Auth.** Google OAuth "Desktop app" client with a loopback redirect on `127.0.0.1:<random port>`, a random `state` value, and PKCE. The only scope is `photospicker.mediaitems.readonly`.
  - The refresh token is stored in the macOS Keychain through the `security` CLI.
  - Port the token engine from `googlehealth/src/google/auth.ts`: the access-token cache with a 60 s buffer, `invalid_grant` cleanup, and rotated-token save.
  - Port the 401-retry wrapper from `googlehealth/src/google/client.ts:14-61`.
  - Do not copy the googlehealth flaws: a secret in the URL, a fixed `state`, and raw Google error bodies in tool output.
  - When no token exists, a tool call opens the consent page automatically and finishes the flow. It never asks the user to run a command.
- **Picker flow, inside one server call.**
  1. Call `sessions.create` with `maxItemCount`.
  2. Run `open "<pickerUri>/autoclose"` in the laptop browser.
  3. Poll `sessions.get` at Google's `pollInterval`, inside the server, until `mediaItemsSet` is true or the session times out. Send MCP progress notifications while waiting.
  4. Page through `mediaItems.list`.
  5. Download with `=d` for photos and `=dv` for videos once READY, using the bearer header and bounded concurrency. baseUrls expire after 60 min.
  6. Call `sessions.delete`.
- **Temp files.** Files go in `$TMPDIR/gphotos-mcp/<session>/<createTime>_<filename>`.
  - The server deletes its folders older than 24 h at startup and its own folders on exit.
  - macOS also purges `$TMPDIR` files that go unused.
  - Claude reads files by path with its normal Read tool, so images enter the chat the same way a dragged file does.
- **Source seam.** `PhotoSource` has two implementations: `PickerSource` (live) and `ReplaySource` (recorded real picks, used only by evals).
  - Only `GPHOTOS_SOURCE=replay:<dir>` selects replay.
  - If the env var is missing or bad, the server fails with a clear error. There is no silent fallback.
- **Server instructions and prompts.** These steer the model on four points:
  - Tell the user what to search for in the picker, such as a place, date, or keyword.
  - Reuse the current manifest for follow-up questions instead of picking again.
  - Read only as many images as the task needs.
  - Run auth automatically.

  The prompts are short XML-sectioned templates for `ingest_photo_set`, `notes_from_slides`, and `diagram_to_mermaid_or_markdown`, written as general frameworks with no sample data.

### Baseline tool set (config C below)

| Tool | Purpose |
|---|---|
| `pick_photos {max_items?, note_to_user?}` | Runs the full flow and returns a manifest: path, filename, createTime, mimeType, width and height, camera, and exposure, sorted by time |
| `list_picked {session?, after?, before?, camera?, type?}` | Filters an earlier manifest without picking again |
| `cleanup_photos {session?}` | Deletes the temp files now |

### Configs (one change each)

- **A.** Low-level tools that mirror the API: `create_session`, `get_session`, `list_items`, `download_item`, `delete_session`. The model polls on its own.
- **B.** A high-level `pick_photos` that blocks, plus `list_picked`. No server instructions or prompts.
- **C.** B plus server instructions and the three prompts. This is the baseline.
- **D.** C plus inline image blocks of up to 20 thumbnails at 1024 px or smaller in the pick result.
- **E.** C, but split into two steps. `start_pick` returns at once, and `wait_for_pick` blocks.

### Tasks, in your real library

Each task's picked set is captured once with a live pick by you at round start. `spe/evals/capture.ts` saves the original bytes and the manifest under `spe/evals/fixtures/rNN/<task>/`, which is gitignored.

- **T1.** Photogrammetry ingest: 100 to 200 photos of one object.
- **T2.** Slide notes from 8 to 12 slide photos.
- **T3.** Diagram to Mermaid: 2 or 3 photos.
- **T4.** Journal page to Markdown.
- **T5.** A mixed pick filtered by a time window.
- **T6.** A follow-up question on T2's set.
- **T7.** Auth revoked partway through.
- **T8.** You ask "photos from <place>". The model should explain that location is not available and tell you which place to search for in the picker.

You write the reference text for T2 to T4 before any trial runs, so the author never writes the judge.

| M4 re-pick rate on T6 (second pick call) | 0.40 ± 0.20 | 0.30 ± 0.20 | 0.05 ± 0.05 | 0.05 ± 0.05 | 0.10 ± 0.10 |
| M5 leftover files or sessions per trial (filesystem diff plus session check) | 0.30 ± 0.20 | 0.00 ± 0.05 | 0.00 ± 0.05 | 0.00 ± 0.05 | 0.00 ± 0.05 |

Why, per metric:
- **M1.** In A the model must poll, paginate, and download 100 or more items one call at a time, so T1 often fails.
- **M2.** T1 dominates A's count. E adds one call.
- **M3.** A's many calls repeat the context. D's thumbnails add image tokens on every task.
- **M4.** Without instructions, the model tends to call pick again for a new question.
- **M5.** In A, cleanup depends on the model remembering to call `delete_session`. In the other configs the server does it.

### Evaluate

- **Harness.** Each trial runs `claude -p --output-format stream-json --mcp-config spe/evals/configs/<X>.json --strict-mcp-config` with `GPHOTOS_SOURCE=replay:<fixture>`. The replay pick finishes after a fixed delay. Code checks run first. An Opus judge scores only the rubric items: T2 to T4 content against your references, and T8 honesty.
- **Gates, in order:**
  1. Grader selftest: the reference passes, and empty or wrong output fails.
  2. No last-round control exists in r01, so log that it was skipped.
  3. Dry run on 3 cells. This measures the real cost per trial.
- **Workflow.** One run covers 5 configs × 8 tasks × 3 trials, holds `ROUND` in a single constant, and scans transcripts to void any trial that reads graders or references.
- **Cost.** The $50 cap is enforced from the measured `total_cost_usd`. If the dry run projects more than $50, the run drops to 2 trials per cell and logs the skips. The cost estimate is not measured until the dry run.
- **Live smoke tier.** After the replay tier passes, config C runs 3 real picks by you: a small T1, T2, and T5. These count against the same cap.
- **Close-out.** Write `spe/prediction-log.md`, `spe/failures.md`, and the round 2 proposals.
